## 严重问题：界面完全不显示（已修复）

**现象**：双击 exe 进程起来了但没有任何窗口。

**根因**：改写 `App.xaml` 时删掉了 `StartupUri="MainWindow.xaml"`，同时 `App.xaml.cs` 是空的类、没有 `OnStartup` 覆写。结果谁都没创建 MainWindow——进程空转，界面永远不出现。

**修复**：`App.xaml.cs` 覆写 `OnStartup`，显式 `new MainWindow()` 并赋给 `MainWindow` 属性后 `Show()`；顺带加了 `DispatcherUnhandledException` + `AppDomain.UnhandledException` 全局兜底，避免以后再出现"界面静默消失无从排查"。

**教训（重要）**：此前用 `timeout 12 ./xxx.exe` 返回码 124 就宣称"程序稳定运行"，这是**错误的验证方法**——124 只证明进程活着，完全不能证明窗口出现过。这类 GUI 程序必须验证窗口句柄。
正确验证方式（PowerShell，无需 Add-Type）：
```powershell
$p = Start-Process $exe -PassThru; Start-Sleep 5; $p.Refresh()
$p.MainWindowHandle   # 非 0 即已创建顶层窗口
$p.MainWindowTitle
```
实测值：句柄 3802944，标题「WPF 串口助手」，40 线程，189MB。后续 GUI 验证一律沿用此法。

## 问题：发送 payload.Length 恒为 0（已修复）

**现象**：文本框输入「测试」点发送，`BuildSendPayload()` 返回空数组，静默不发送。

**根因**：发送区两个输入框的 Visibility 转换器**装反了**——
- 文本框(绑定 SendText) 用了 `BoolToVisibilityConverter`(true→Visible)，导致文本模式下它反而隐藏；
- HEX框(绑定 SendHexText) 用了 `InverseBoolToVisibilityConverter`，文本模式下它反而显示。
用户在文本模式下看到的其实是 HEX 输入框，「测试」进了 `SendHexText`；而 `SendHexMode=false`
时 `BuildSendPayload()` 走 `Serial.Encoding.GetBytes(SendText)`，SendText 为空 → 长度 0。
且 `Send()` 对空 payload 是静默 return，没有任何提示，所以表现为"点了没反应"。

**修复**：① 交换两个转换器；② `Send()` 空 payload 时弹窗提示（分别说明文本/HEX 模式该怎么填）；
③ `SendHexText` setter 里实时调 `UpdateHexError()` 校验并显示错误位置（原先 `SendHexValidation`
属性没有绑定方，getter 永远不会被触发，校验形同虚设）。

**验证（--diag 复用）**：临时诊断检查了 4 项——文本模式文本框可见/HEX框隐藏、HEX模式相反、
SendText="测试" 经 UTF-8 编码为 6 字节(E6B58B E8AF95)、"01 GG" 能报"第 4 个字符处不是合法 HEX 数据"。
全部通过后删除诊断代码。

**探针踩坑**：窗口里有 6 个 TextBox（含只读日志框、过滤框、循环参数框），按 Name 或
`!IsReadOnly` 筛选都会抓错对象，必须按 `GetBindingExpression(TextBox.TextProperty).Path.Path`
精确匹配 `SendText`/`SendHexText` 才可靠。

## 关键认知：UartAssist 的「ASCII」不是严格 7-bit ASCII（已按此修正）

**问题**：用户反馈 UartAssist 两边都选 ASCII，却能正常收发中文；而我方选 ASCII 发出的是 `3F 3F`。

**真相**：那类工具（UartAssist、串口调试助手等）所称的「ASCII」只是相对「HEX 模式」而言的
**"文本模式"**称呼，底层按**系统 ANSI 代码页**编解码（中文 Windows 上是 936/GBK），所以中文正常。
而 GBK 在 `0x00-0x7F` 范围内与严格 ASCII 字节完全一致，因此 AT 指令等纯英文数据不受任何影响。
真正用 `Encoding.ASCII`（严格 7-bit）反而与 UartAssist 行为不一致。

**修复**：
1. `TextEncodingOption` 的 "ASCII" 选项改为 `GetAnsiEncoding()`：
   取 `CultureInfo.CurrentCulture.TextInfo.ANSICodePage`，取不到则退回 936。
2. 实测：`ASCII("测试")` → `B2E2CAD4`（GBK），`ASCII("AT+RST")` → `41542B525354`（与严格 ASCII 一致）。

**顺带修掉的潜在崩溃 bug**：`.NET Core` 默认不含 GBK/Big5 代码页，`Encoding.GetEncoding(936)`
不注册 provider 会抛 `NotSupportedException: No data is available for encoding 936`。
即原来选择 GBK/GB2312/Big5 会直接异常。已加 `System.Text.Encoding.CodePages` 9.0.0 包，
并在 `TextEncodingOption` 静态构造函数里 `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)`。
实测 7 个编码全部可创建（ASCII→gb2312、GBK→gb2312、Big5→big5 等）。

**告警逻辑同步升级**：`ShowAsciiWarning` → `ShowEncodingWarning`，不再硬编码判断 ASCII/Latin-1，
改用 `EncoderFallback.ExceptionFallback` 试编一次精确判定是否丢字符（只采样前 500 字符）。
实测：ASCII+中文→false，Latin-1+中文→true，Latin-1+英文→false，ASCII+中英混合→false。

**注意**：配置文件里 16:01 那条 `"EncodingName": "GBK"` 是用户自己关程序时保存的，不是探针写的。
因 ASCII 与 GBK 底层同为 936、行为一致，已按用户要求改回 `"ASCII"`。

- 逻辑层：`ModbusRtu.TryParseUshort` 既有规则已对齐 —— `0x` 前缀时 hex 长度 ≤ 4；纯数字时长度 ≤ 5 且走 `ushort.TryParse`（拒 65536）；纯字母形式长度 ≤ 4

**边界验证**（临时工程引用 `ModbusRtu.cs`+`HexConverter.cs`，验证后已删除）17 项全过：
`0xFFFF/0xffff/FFFF`→65535，`0x12345`/`0x123456`/`65536`/`123456`/`0x`/空串→拒绝，`12345`→12345。
边界帧 `01 03 FF FF 00 01` → `01 03 FF FF 00 01 84 2E`（8 字节，无溢出）。

**注意**：`"abc"` 会被解析成 `0x0ABC`（纯十六进制字母按 HEX 解读），是既有设计不是 bug，写测试时别按「应拒绝」断言。

## 内存显示口径改为「专用工作集」（与任务管理器一致）

用户发现界面显示 179.6 MB、任务管理器只有 90.8 MB。

**原因**：`Process.WorkingSet64` 是完整工作集，包含共享 DLL（.NET 运行时、WPF/Microsoft.WindowsDesktop 模块）映射的共享页；任务管理器内存列是「专用工作集」(Private Working Set)，只算进程独占的物理内存。

**修复**：
- csproj 加包 `System.Diagnostics.PerformanceCounter` 9.0.0
- `MainViewModel` 用性能计数器 `Process\Working Set - Private` 取值，与任务管理器同源同口径；读不到时回退 WorkingSet64
- 定位计数器实例不能用名字猜（多开时带 #1/#2 后缀），用「ID Process」计数器按 PID 精确匹配
- 首次 NextValue() 可能返回 0，此时该秒回退完整工作集，下一秒自动恢复

**核对**：独立 `Get-Counter` 读同计数器得 99.6 MB（完整工作集 184.1 MB），比例与用户截图一致，UI 绑定同一计数器。

## 启动耗时优化（1.8s → 1.0s）

**定位方法**：外部 Stopwatch 轮询 MainWindowHandle 测总时长 + 临时插桩分段计时（跑完删除）。

**根因**：上一轮加的内存显示，在 `MainViewModel` 构造里同步调用 `UpdateMemoryUsage()`，
其中 `new PerformanceCounterCategory("Process").GetInstanceNames()` 要枚举系统全部进程实例，
**实测吃掉整整 1 秒**（消融实验：注释掉该调用 1.7s → 0.72s）。

**修复**：
- `TryGetPrivateWorkingSetMb` 不再自己触发探测，计数器为空直接返回 false
- 新增 `StartPrivateWorkingSetProbe()`：`Task.Run` 后台找计数器，完成后 `BeginInvoke` 回 UI 线程并置 `_privateWsProbeDone`
- 探测未完成时 `MemoryDisplay` 保持 `--`；探测失败退回完整工作集；`Dispose` 用 `_disposed` 防止回调悬空

**分段耗时（Release）**：进程→OnStartup 434ms（runtime/WPF 程序集加载）、XAML 解析 237ms、首帧渲染 293ms、
VM 构造仅 9ms。即剩余成本是 WPF 冷启动固定开销，业务代码无水分。

**打包形态实测**（均为热启动，冷启动=首次运行需解压）：
| 形态 | 热启 | 冷启 | 体积 |
|---|---|---|---|
| 压缩单文件（现用） | ~1000ms | ~2.4s | 61MB |
| 不压缩单文件 | ~812ms | ~5.5s | 128MB |
| 不压缩单文件+R2R | ~712ms | ~8s | 144MB |
| 压缩+R2R | ~1040ms | ~7s | 64MB |
| 文件夹发布 | ~760-970ms | ~970ms（无解压） | 136MB/251 文件 |

结论：R2R 在压缩下无收益；压缩本身约 +200ms；冷启动慢是单文件解压（每版本一次）。
最终保留压缩单文件，体积与体验平衡最好。

**验证**：`--checkmem` 临时开关跑 3 秒读 `MemoryDisplay` = `101.0 MB`（与 Get-Counter 同口径），确认后台探测正常，验证后已删。

## 评估：加 TCP / UDP 通讯（结论：暂不实现，已记录路线）

**现状耦合度（实测）**：`_serialPort` 在 MainViewModel 出现约 12 处，全部走
`Open/Close/Send/DiscardInBuffer/TotalReceived/TotalSent` + 3 个事件，抽象成本低。
收发管道（队列 → 50ms 批量 → 日志着色 → 统计）已是 byte[]，与传输无关，可直接复用。

**主要工作量**：ITransport 抽象 2-3h；TCP 客户端 2-3h；UDP 1.5h；
TCP 服务端（多客户端/会话选择）4-6h；UI 模式切换 3-4h；配置 1h；测试 2-3h。

**已知坑（下次动手前先看）**：
- TCP 粘包/拆包：现有 50ms 聚合按块显示，TCP 可能半帧或粘两帧，需支持分隔符/长度分帧
- UDP 应一个 datagram 一个日志块，不能套用 50ms 聚合
- TCP 服务端需"会话"概念（发给谁、日志标来源）
- Modbus 构造器输出 RTU+CRC16，Modbus TCP 要 MBAP 头，不可混用
- 断线重连、端口占用、防火墙提示

**建议分期**：①ITransport + TCP 客户端 + UDP → ②TCP 服务端 → ③Modbus TCP。
